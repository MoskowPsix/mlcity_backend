## Роли и зоны ответственности

| Роль | Зона |
|---|---|
| Lead | Контракты, нарезка задач в YouGile, приёмка сценариев, decision-log, эскалация руководству |
| Developer A | Вокруг (`mlcity`): доступ, чекбокс, комиссия, API импорта (этапы 1–2) |
| Developer B | Чекпоинт (`hrono-app`): своя дисциплина, импорт, метки, заезд (этап 2) |
| Stage3 | Весь этап 3 в одном потоке: `hrono-back` (checkpoint API + forward) + клиент Чекпоинта + UI/share на карточке Вокруг (рекоменд. Developer B) |

## Работа с документацией

### Кто читает и кто изменяет

| Документ | Читают | Изменяют |
|---|---|---|
| Контракт импорта + fixtures | A и B (обязательно) | Lead; ломающие правки — запись в decision-log + bump версии |
| Контракты 06 / 08 (результаты) и типы заезда (09) | Stage3 и B (по зоне) | Lead |
| Карта экранов | A и B / Stage3 (по зоне) | Lead |
| Задачи этапов 1–2 | A и B; текст переносится в YouGile | Lead |
| Задачи этапа 3 (`07`) | Stage3; текст переносится в YouGile | Lead |
| Правила приёмки | Вся команда | Lead |
| Чеклист мотокросса | B (A — если затрагивает общее) | Lead; результат прогона — в комментарии YouGile к E2-10 |
| Decision-log | Вся команда | Lead; предложения от разработчиков — через YouGile/чат, затем запись в лог |
| Описание и этапы для руководства | По необходимости на kickoff | Lead / руководство |

### Поток «задача → документ»

1. В YouGile создаётся карточка по шаблону из `03-yougile-tasks-stage-1-2.md` (полный текст или краткое описание + ссылка).
2. В карточке указываются пути, например:  
   `Контракт: docs/checkpoint/01-import-contract.md §3.2`  
   `Мок: docs/checkpoint/fixtures/competition-import-mock.json`
3. В командный чат — короткий статус и номер задачи YouGile, без длинных копий JSON.
4. Имена полей и статусов берутся из контракта, а не из устных договорённостей.

Приоритет источников: **контракт / decision-log > YouGile > чат > память**.

### Decision-log

- Новые продуктовые и архитектурные решения фиксирует Lead.
- Разработчик не меняет лог самостоятельно. Предложение — в YouGile или чат; после согласования — запись в лог, при необходимости обновление контракта и критериев задачи.

### Kickoff

1. Показать структуру `docs/checkpoint/` в репозитории.
2. Закрепить правило приоритета источников.
3. Назначить зоны A/B и первые задачи YouGile со ссылками на документы.
4. Уточнить: decision-log читает команда, изменяет Lead.

### Чего избегать

- Пересылать в чат фрагменты JSON без пути к файлу в репозитории.
- Дублировать весь контракт в каждой карточке YouGile.
- Менять контракт без согласования Lead (риск расхождения A и B).

## Ритм работы

- Понедельник (30–45 мин): план недели, блокеры.
- Ежедневно: короткий статус в чате или YouGile.
- Четверг/пятница: приёмка колонки «На проверке».
- Раз в 1–2 недели: сверка с этапами для руководства.

Колонки YouGile: **Бэклог → На уточнении → В работе → На проверке → Готово**.
